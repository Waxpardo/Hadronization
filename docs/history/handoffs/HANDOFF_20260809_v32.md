## 3. THE GATE — running, and its sizing plan was wrong in an instructive way

`docs/GATE_3000.md` carries the pre-registration. Cluster **`5399180`**, batch
node, serial. Log `gate_runs/gate_3000.log`, report `gate_3000_report.json`,
sentinel **`GATE_3000_DONE`** written *whatever the exit code*, so a failure is
distinguishable from a job that never finished.

### It has no pool. That is not a tunable.

The brief asks for P = 4–8, sampled and re-derived. **There is no P.**
`validate_analysis_outputs.py` takes no concurrency argument, and adding one is
not local: `:570-576` writes the single report `merge_root_files.sh:80-84`
consumes, and the whole-set checks (`:371-383` staging/extras/missing;
`:535-537` single-valued commit, macro and stability hashes) are **meaningless
over a shard**. `HANDOFF_20260806_v9.md:118` said so; re-verified, not inherited.

### The `441 MiB` figure is CONFIRMED, not superseded

25 independent single-directory measurements:

| | measured |
|---|---|
| maxRSS mean | **452,924 kB = 442.3 MiB** |
| maxRSS spread | **0.9 %** (449,244 – 453,480 kB) |
| wall mean / median | **25.43 s / 23.87 s** (range 17.10 – 38.74) |
| CPU/wall | 0.799 |

**442.3 against an inherited 441 — 0.3 %.** A number carried four generations on

"re-derive all pool sizing from v3" as one instruction would have mixed them.

**Memory does not bind. Wall time does** — one process at 442 MiB against 4 GB
requested. That inverts the assumption the whole pool arithmetic rested on.
