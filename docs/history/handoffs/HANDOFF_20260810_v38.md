### The cross-check is passing

The exact block sums come from a scratch macro reusing the production cut strings
verbatim, because the production macro prints the baryon splits only as
percentages to 2 decimals — reconstructing counts from those is lossy at
**±10 candidates per file**, ~0.1 % of a block total, which is **twenty times the
shift being measured** for MONASH. So the sums use exact integers and the driver
cross-checks its replication against the production macro on one file per tune
per block:

```
XCHECK_OK unresolved_n=163  resolved_n=197743  measured_baryon_pct=4.6702   (MONASH)
XCHECK_OK unresolved_n=2340 resolved_n=199231  measured_baryon_pct=17.7538  (CR)
XCHECK_OK unresolved_n=2200 resolved_n=197669  measured_baryon_pct=17.2379  (CR)
XCHECK_OK unresolved_n=152  resolved_n=197942  measured_baryon_pct=4.7418   (MONASH)
```

**The pre-registered structure is already visible**: the CR tunes carry ~2,300
unresolved candidates per file against MONASH's ~160 — **an order of magnitude** —
exactly as the macro's own header predicted qualitatively. **The shift's sign and
size remain the measurement; no expectation was stated and none is stated now.**

**Aggregation convention** (`tools/aggregate_m7.py`): central values from
**pooled counts** over all ten blocks, uncertainty from the **block spread**
(`stdev/√10`). A mean of per-block ratios is not the ratio of the sums; the
whole-campaign ratio is what the paper quotes. It **fails closed** on fewer than
ten blocks, which would compute a SEM over the wrong n.
