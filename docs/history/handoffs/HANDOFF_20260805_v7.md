## 3. Corrections to the brief — evidence, not disagreement

**3a. The memory cap is host-dependent, and I got this wrong first.** I
originally wrote that the 2.00 GiB cap "does not exist" and filed it as another
390-CPU-hours phantom. **That was wrong and the owner corrected it.** Both
figures are real measurements of different machines:

| Host | Scope | `memory.max` | How established |
|---|---|---|---|
| **login node** | user slice | **2.00 GiB** | The `ValidatePairBlockClosure` OOM: a real kernel kill, `constraint=CONSTRAINT_MEMCG`, `anon-rss:1996592kB`. It is what motivated the leak fix |
| **`stbc-i3`** (batch) | `user-11484.slice` | **128 GiB** | Measured this session; session scope unlimited, `ulimit -v`/`-m` unlimited, 503 GiB RAM |

**The correct statement is "2.00 GiB on the login node, 128 GiB on stbc" — not
"the cap does not exist".** This is operationally load-bearing: **running the
merge or the closure from the login node is the natural thing to do, and
earlier sessions did exactly that.** Anyone who does hits 2 GiB. Compare any
measured peak against **2097152 kB**, not against 128 GiB, unless you know the
run is pinned to a batch node. **This session's merge ran on `stbc-i3`**, so
its peak is measured under the generous cap and must be checked against the
strict one before anyone concludes it is safe.

**The distinction it was missing was a host, not evidence.** Unlike the 390
CPU-hours, this number was measured; it simply was not attributed. That is a
different and much less serious defect, and treating the two as the same
pattern was my error.

Separately, no 2 GB *Condor request* exists — analysis jobs request 8 GB
(`tools/render_analysis_submit.py:282`), production 4 GB
(`tools/render_production_submit.py:275`). That remains true and is unrelated
to the cgroup cap.

**Also worth a number rather than a note:** `ulimit -t = 115200` is a **32-hour
CPU ceiling per process**. `MEASUREMENTS.txt` now extrapolates the merge's CPU
time — not wall clock — to 3000 files and compares it. If the stage is
I/O-bound, CPU accrues well below wall time and there is headroom; if it is
not, **a single-process merge cannot complete full production at all**, and B10
becomes a hard structural requirement rather than a wall-clock convenience.

**3b. The "30-file baseline" is 10 files per tune, 30 total** — and therefore
HF_PT2's `inputs_per_block` was **1**. That is exactly why the intra-block
summation path has never run with more than one input, and why this campaign at

**Added this session, earned the hard way: kill by recorded PID only, never by
pattern match, on any shared host.** `pkill -u $(id -un) -f summarize_merge.py`
matched **its own ssh command line** — the pattern appeared in the remote
command string — and killed the shell running it, so the intended relaunch never
executed. **The merge survived by luck of pattern, not by design:** had the
pattern been broader, or had the merge's command line contained the matched
substring, a 70-minute run would have died silently and been discovered only by
the absent `EXIT` file. Every long-running process already has its PID recorded
at launch, so the safe form costs nothing:

```bash
# read the PID from /proc/<pid>/cmdline, never match on the caller's own args
OLD=$(pgrep -u "$(id -un)" -x python3 | while read p; do
        tr '\0' ' ' < /proc/$p/cmdline | grep -q summarize_merge && echo $p; done)
[ -n "$OLD" ] && kill "$OLD"
```
