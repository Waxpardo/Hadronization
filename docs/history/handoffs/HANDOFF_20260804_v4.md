### 7a. DIAGNOSED — it is a pre-existing memory leak, and it breaks the merge

Everything below is **measured**, not inferred.

**The cap.** `/sys/fs/cgroup/user.slice/user-11484.slice/memory.max =
2147483648` — exactly 2.00 GiB, on the *user slice*, i.e. shared across all of
the user's login sessions. The node itself has 7.9 GB total / 6.4 GB available,
so this is a per-user cap, not node exhaustion.

**The kill.** From `dmesg`:

```

Memory cgroup out of memory: Killed process 2408507 (root.exe)
  total-vm:4496644kB, anon-rss:1996592kB
```

**The shape.** RSS sampled every 3 s over the closure run for MONASH:

| elapsed s | 3 | 19 | 43 | 67 | 92 | 116 |
|---|---|---|---|---|---|---|
| RSS MB | 221 | 744 | 1203 | 1680 | 2160 | 2296 |

Monotonic, linear, ~20 MB/s, **no plateau**. A working set plateaus; this does

**The mechanism, proven directly.** `THnSparse` does not inherit `TH1`, so it
does not participate in `TH1::AddDirectory` adoption: `TFile::Get()` hands
ownership to the caller, and `ValidatePairBlockClosure.C` never deletes what it

```

LEAKTEST delete_after_use=yes iterations=40 growth_MB=2
```

**Two hypotheses ruled out by measurement.** It is not the count of open files:
11 files with 5 objects each retained only ~27 MB. It is not the transient
`SparseEqualsBlockSum` maps: those are function-local and the per-object
maximum over all 300 files is `hTrKinematics` at 130,248 bins, *larger* than
`hFlavourClosure` at 125,475, so adding the latter could not have raised a
map-driven peak.

**Why `b01536b` tipped it over.** Scanned across all 300 central MONASH pair
files:

| object | mean filled bins | max filled bins |
|---|---|---|
| `hTrKinematics` | 49,117 | 130,248 |
| `hAsKinematics` | 1,085 | 28,756 |
| `hCorrelations` | 1,091 | 28,993 |
| `hCorrelationsByOrigin` | 1,091 | 28,993 |
| **`hFlavourClosure`** | **46,903** | **125,475** |

The four previously-checked objects total 52,384 mean bins per file;
`hFlavourClosure` adds 46,903, **a factor 1.90 on the leaked volume**. The
four-object run fit under 2.00 GiB with modest headroom; nearly doubling it

**So `b01536b` exposed a pre-existing defect rather than creating one — but the
