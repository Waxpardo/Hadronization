## Objective

Unchanged. A PYTHIA 8 generator-level study asking: when a heavy quark from a
hard scattering ends up in an identified hadron, which hadron carries the
compensating anti-flavour, and where is it? Three hadronisation configurations
(MONASH, JUNCTIONS, CLOSEPACKING) at √s = 13.6 TeV; the discriminating question
is whether the balancing partner of a heavy-flavour *baryon* is itself a baryon
or a meson. Deliverable: a peer-reviewed publication plus a reproducible public
repository.

## Key Decisions

Unchanged from the previous handoff except as noted.

| Decision | Why |
|---|---|
| **Delete the gate layer** | 4:1 process:physics. **The 2-bit tune ordinal was NOT a reason** — see below. |
| **Job size/count are arguments, not schema constants** | They carry no physics. The `N>=100` floor and `kFirstStageSlots` that encoded one campaign shape are both already gone. |
| **`pTHatMin = 2.0`** | Now documented as `docs/DESIGN_AND_RATIONALE.md` §3.12, which did not exist before. At 1.0 the sample was 28.6 % below minimum bias on 8.317 (36 % was the 8.315 figure); at 2.0 it is within 4.2 %. |
| **Hang guard on CPU, not wall clock** | **Vindicated this session.** The HF_PT2 hang ran 3616 s wall against a 14400 s wall guard — a wall-clock guard would not have fired for another ~3 hours. The CPU guard caught it at 3612 s. |
| **Retries use fresh seeds** | Used exactly once this session; worked. |
| **`JUNCTIONS_MATCHED` is NOT run** | **Strengthened:** it is not merely unused, it is *not producible*. `TuneOrdinal` (`HeavyFlavourUtils.h:396-401`) maps three tunes; the producer whitelist (`heavyflavourcorrelations_status.cpp:124`) has four. Such a job throws at its first event. Given it must never run in production, that throw is a fail-safe. Its card exists so `make cards` can verify its fragmentation values are the Monash defaults (`validate_tune_cards.py:58-71`) — that check is its whole purpose. |
| **Tune list has one source** | `campaign.PUBLISHED_TUNES`. Six Python sites migrated. Four C++/shell sites remain: `TunePlotStyle.h:13`, `Validate_THnSparse_Production.C:44`, `Plot_InclusiveKinematicSpectra_Raw.C:789,1953`, `merge_root_files.sh:186,202`. |

### On the 2-bit tune ordinal

Two bits hold ordinals 0–3 = exactly four configurations. The study defines
four. **It binds only on a fifth.** Widening is cheap in principle — take two
bits from `campaign:16`, whose ordinal is currently 1 — but changes the meaning
of every stored `event_id`, forcing a raw-schema bump across 23 files and
superseding all existing production. **That is far cheaper before the full
campaign than after it.** If a fifth arm is ever wanted, decide before
`make submit-full`. Now recorded in `DESIGN_AND_RATIONALE.md` §3.11.

### Constraints that must be respected

Unchanged: sign convention by quark content; trigger requires hard-origin
ancestry and associate does not; ambiguity is never tie-broken; ten disjoint
blocks with SEM and `conservative_degrees_of_freedom = 9`; raw files cannot be
merged; PYTHIA is built `-std=c++20` and ROOT's `--cflags` wins over the
Makefile's `-std=c++17`; **no design choice may exist only in code.**

Six decisions that violated that last rule are now documented — `DESIGN` §3.12
(pTHatMin 2.0) and §3.13 (the pair-file object contract including why
`hFlavourClosureSummary` is permitted but not required; the 300-file campaign
shape asserted as literals in two shell validators; `plot_provenance_tool=""`).

## BLOCKING PRECONDITIONS ON FULL PRODUCTION

`make submit-full` does not happen until every item here is closed. Each is
cheap now and expensive later, which is the whole reason they are listed.

**1. The raw-validation receipt schema mislabel.**
`run_status_analysis.sh:225,341` records `raw_validation_receipt_schema` as the
literal `"hf_raw_validation_receipt_v1"`, and
`tools/validate_analysis_outputs.py:417` requires exactly that. The real
receipts are `v2` (soon `v3`). The two agree with each other, so nothing fails
-- the label is simply wrong, and it is now baked into the 30 promoted HF_PT2
analysis directories.

It was left alone deliberately: correcting it while those directories existed
would have made `merge_root_files.sh:81` reject all 30, which is the same
fails-hours-later failure mode that the raw_schema v5/v7 defect had. Sequence:

  a. rungs 5 and 6 run against HF_PT2 as it stands, mislabel included;
  b. once rung 6 is green, fix BOTH sites together, re-run the HF_PT2 analysis
     (30 jobs, cheap now the path is proven) and confirm the merge still passes;
  c. only then `make submit-full`.

A wrong receipt-schema label baked into 3000 analysis directories instead of
30 is the version of this problem that cannot be afforded.

**2. The tune-ordinal width.** Two bits hold four configurations and the study
has four, so nothing is constrained today. Widening later forces a raw-schema
bump across 23 files and supersedes all existing production -- trivial before
a full campaign, 100x worse after it. Decide explicitly before submitting; see
`docs/DESIGN_AND_RATIONALE.md` section 3.11.

**3. The multiplicity offset is measured for MONASH only.** The -4.2 %
minimum-bias offset justifying `pTHatMin = 2.0` was measured on MONASH alone
(`ValidationReports/PTHAT_MULTIPLICITY_SCAN_8317.md:108-110`). JUNCTIONS and
CLOSEPACKING have different MPI screening scales (`pT0Ref` 2.15 and 2.194
against MONASH's 2.28), so their offsets differ and are unmeasured. Event
activity is classified by percentile *within each tune's own sample*, so if the
offsets differ then "0-20 %" is not the same physical selection across tunes --
and multiplicity dependence is central to the study. Re-running
`Validation/CalibrateMultiplicityAgainstMinBias.C` for the other two tunes is
about four minutes of login-node time.

**4. `config/dataset_selector.json` has no canonical entry.** Its only dataset
is `legacy_21_06_2026`, `status: legacy_regression_default`,
`publication_eligible: false`. `run_paper_plots.sh:223-232` is fail-closed:
every publication plotting target refuses unless the active dataset is
`canonical` or `canonical_candidate`. Rung 6 cannot run until an entry pointing
at the HF_PT2 merged output exists. This is a config addition, but choosing
between `canonical_candidate` (publication-ineligible by construction) and
`canonical` (which additionally requires an authorization record) is a
decision, not a default.
