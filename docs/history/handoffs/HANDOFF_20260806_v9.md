## 0. Read this first — a hazard that nearly cost all 33 promoted directories

**Re-running the checksum gate in place would have invalidated every promoted
merge directory.** `merged_pair_provenance.py:146` records
`analysis_output_validation_sha256` — the sha256 of
`analysis_output_manifest_validation.json` — inside each promoted directory's
`merge_provenance.json`. Rewriting that report changes the hash and every
promoted directory then fails `validate`.

**The gate is re-runnable for timing ONLY with `--report` omitted**
(`validate_analysis_outputs.py:292` makes it optional; with it absent the tool
does all the work and writes nothing). **This is how the P=1 sweep was
launched.** Verified after launch by reading `/proc/<pid>/cmdline` — zero
occurrences of `--report`.

**A real safety property, worth knowing:** `:570-576` refuses to overwrite a
report whose content differs, so a mistake here is caught rather than silent.
It is a guard, not a licence — do not rely on it.

### P=4 and P=8 are NOT yet designed, and here is the trap

**`validate_analysis_outputs.py` has no pool and cannot be sharded without
changing a contract** — `:570-576` writes the single report
`merge_root_files.sh:80-84` consumes. So a sharded run measures **only the
per-directory unit**: the loop body at `:374`–`:530`, dominated by
`validate_pair_directory()` (`:506`, spawns ROOT) and `directory_digest()`
(`:523`, sha256 over ~97 MB of ROOT files per directory).

**Therefore the P=4/8 numbers are NOT comparable to P=1 without stating the
serial remainder.** `whole-gate P=1` minus `sum of per-directory units` is that
remainder, and it is the Amdahl bound on what any pool can buy. **Compute and
state it. Do not report a speedup without it** — comparing a sharded
per-directory harness against the whole gate would be the fifth scope error in
this project.

**This is a MEASUREMENT, not the implementation.** The checklist may carry
"measured speedup X at P=8, implementation pending". Do not build the pool.
