## 3. THE HOOK — the guard, reinstalled where a checkout move cannot remove it

`tools/install_checkout_guard_hook.sh`, **installed on
`/data/alice/ipardoza/Hadronization`**. Documented in `docs/WORKSPACE.md`.

**Why a hook.** `.git/hooks/` is not part of the working tree, so it survives
checkout moves — which is precisely how the Makefile guard was lost. The hook is
**self-contained**, re-implementing the two-condition probe rather than importing
`tools/queue_probe.py`, which the pinned tree does not have.

**`reference-transaction` is the only hook that can hold the invariant.**
`post-checkout` runs *after* the move and can only warn. `pre-merge-commit` does
not fire for a **fast-forward** — exactly how a pin gets advanced.

- Narrowed to updates that move **HEAD** or the branch HEAD points at. **`git
  fetch` is not blocked** — verified.
- **Fail-closed.** `condor_q` is **not installed on the login node**, so the
  probe returns UNKNOWN and the move is refused there. That is correct: a host
  that cannot ask whether jobs are in flight should not move a pinned checkout.
  **Move the checkout from `stbc`.**
- Override records a reason to `.git/checkout_guard.log`, `OVERRIDE` distinct
  from `ALLOWED`:

```bash
HADRONIZATION_CHECKOUT_OVERRIDE_REASON="restoring the pin to <sha>" git checkout <sha>
```

**Verified live, both directions.** Real `git checkout` refused with `fatal: ref
updates aborted by hook` (exit 128, HEAD unchanged), then succeeded under a
recorded override — **exercised in a throwaway `--local` clone**, so proving the
abort never risked the pinned repo. On the pinned repo the installed hook
(byte-identical by sha256) was driven through its real interface both ways:
refuse `exit 1` on UNKNOWN (login) and on NONEMPTY (`stbc`, 2221 jobs), allow
`exit 0` under a recorded reason. **A HEAD-moving `git` command was deliberately
never run against the pinned repo.**
