# Processing pipeline

## Dataflow and sources of truth

The processing chain has five stages with an immutable raw-file boundary after generation.
Generation is expensive and runs once, while downstream processing is cheaper and can rerun when the question changes.
The producer writes each raw file, and every downstream ROOT consumer opens raw files read-only.
`generation/submit/runCondorJob.sh` and `analysis/status_analysis_THnSparse_qq.C` implement this boundary.

```text
tune card -> generation -> raw file -> reduction -> pair directory
          -> merging -> merged product -> extraction -> tables -> plotting -> figures
```

| stage | input authority | output boundary |
|---|---|---|
| 1. Generation | tune card, generated registries, rendered job row | one validated raw file |
| 2. Reduction | sealed manifest row and raw-file metadata | one validated 300-file pair directory |
| 3. Merging | central and block manifests | one validated merged product per merge leg |
| 4. Extraction | merged products, species ordinals, and decay map | CSV and JSON result products |
| 5. Plotting | selected dataset, plotting configuration, or committed tables | staged figures; accepted bytes enter `results/figures/main/` |

The authoritative boundary artifact changes at each stage.
Raw validation receipts establish raw-file acceptance, and the sealed manifest fixes their ordered union.
The generated pair-object contract defines a pair directory and every merged product.
The species ordinal artifact and decay map define extraction, while the dataset selector fixes ROOT plotting inputs.

The retained campaign record reports 3,000 raw files and 300 million successful events.
It reports 1,000 files with 100,000 events for each of three tunes.
`Makefile` declares this production shape, and `config/dataset_selector_hf_run3_v1.json` records the selected campaign.
The scientific comparison is bundle-to-bundle across the three complete MONASH, JUNCTIONS, and CLOSEPACKING configurations.

## Configuration and generated registries

Hand-edited JSON files define registries and contracts; generated files carry those definitions into C++ consumers.
`tools/generate_registry_artifacts.py` reads `config/heavy_flavour_species_v1.json` and `config/pair_registry_definition_v1.json`.
It writes the generated C++ registries and `config/heavy_flavour_pair_registry_v1.json` with source digests.

The species registry contains 50 signed ground states: 24 charm states and 26 beauty states.
The pair definition selects six triggers in each sector and all same-sector associates.
It therefore expands to `6 * 24 + 6 * 26 = 300` signed, ordered pairs.
The expanded registry records every filename, sign, reference meson, and publication-eligibility flag.

The pair-object JSON is the sole definition of pair-file contents.
`tools/generate_pair_object_contract.py` turns its 66 object rows and two schema tags into `contracts/GeneratedPairObjectContract.h`.
The pair-directory validator, closure validator, and plotting validator filter that header instead of maintaining separate lists.

The 202-species ordinal axis has a separate generated contract.
`contracts/species_ordinals_v2.json` fixes the ordinal-to-PDG mapping and digest `646f310f78126267`.
`tools/generate_species_ordinals_header.py` carries both values into `contracts/GeneratedSpeciesOrdinals.h`.

Every v3 pair file stores the species schema, labels, and digest.
The pair-object contract marks all three values as required invariants across a central and its blocks.
`contracts/decay_parent_map_v2.json` also records the ordinal digest, and `extraction/apply_decay_map.py` refuses a mismatch.

The decay-map builders produce versioned artifacts instead of relying on hand-written lookup tables.
`tools/build_decay_parent_map.py` builds the charge-conjugated map from a pinned PYTHIA probe and the ordinal table.
`tools/build_decay_parent_map_v2.py` adds the registered branching-fraction splits and preserves the same ordinal digest.

Run the generators in check mode after changing a source definition.

```bash
python3 tools/generate_registry_artifacts.py --check
python3 tools/generate_pair_object_contract.py --check
python3 tools/generate_species_ordinals_header.py --check
```

Do not edit generated registries or headers directly.
The `--check` commands compare regenerated bytes with the committed files and fail on drift.

## Event generation and raw schema

Stage 1 generates forced hard-heavy events from one tune card per tune.
Each nominal card enables `HardQCD:hardccbar` and `HardQCD:hardbbbar` at 13.6 TeV with `PhaseSpace:pTHatMin = 2.0`.
The renderer replaces the cards' development event count with the job's requested 100,000 successes.
`tools/campaign.py` performs that materialization before it calculates the effective-card digest.

`generation/producer/Makefile` builds `heavyflavourcorrelations_status` against the configured ROOT and PYTHIA runtime.
The executable accepts the following interface:

```text
MODE OUTPUT SEED CAMPAIGN CAMPAIGN_ORDINAL LOGICAL_ID ROLE ATTEMPT
```

Direct execution produces no campaign receipts and cannot supply a publication input.
Canonical jobs must use the rendered worker path.

One tune card produces files named `raw/<TUNE>/hf_<TUNE>_jobNNN.root`.
The full campaign requires 1,000 files per tune and three published tunes.
`generation/submit/runCondorJob.sh` writes an attempt-specific partial before promoting that stable name.

Every job records the repository commit, tune-card digest, producer-binary digest, and seed.
The worker refuses to start when the checkout, card, or binary differs from the rendered job row.
Raw validation checks the recorded seed and the remaining job identity before promotion.

The producer writes raw schema `hf_primary_ground_raw_v7`.
Its event tree stores process identity, weights, hard-pair kinematics, multiplicity counters, and heavy-hadron vectors.
Those vectors retain signed constituents, origin resolution, ancestry, four-vectors, lifecycle flags, and central-registry membership.
`generation/producer/heavyflavourcorrelations_status.cpp` defines the branches and accompanying metadata trees.

Producer initialization makes every recognized charm or beauty hadron stable before PYTHIA starts.
It records the original and final decay flags and refuses any recognized heavy hadron that remains decay-enabled.
The event loop counts successful events, failed attempts, and tree entries separately.
Raw validation requires `attempts = successes + failures` and `tree entries = requested successes`.

The raw schema also stores an auxiliary light-hadron compensation grid.
It contains net electric charge in thirds and net baryon number on 16 azimuth cells by 8 pseudorapidity cells.
The 128 cells cover `|eta| <= 4` and include charged or neutral final light primaries.

The grid is trigger-agnostic.
An analysis can recover relative-azimuth or relative-pseudorapidity profiles by shifting its cell indices around a chosen trigger.
`generation/producer/HeavyFlavourUtils.h` defines the grid and labels it auxiliary.
It is not a validated charge-balance or baryon-balance observable.

The job metadata binds the raw file to its scientific contracts.
It includes raw, selector, origin, stability, effective-settings, multiplicity, light-grid, registry, and tune-allowlist identifiers and digests.
`Validation/ValidateRawOutput.C` requires those fields and rejects incomplete or inconsistent successful-event accounting.

## Campaign rendering, seeds, and attempts

Stage 1 rendering fixes every job before submission.
`tools/render_production_submit.py` requires a clean commit, calculates the producer and effective-card digests, and emits closed-environment job rows.
The renderer refuses a different pre-existing submit file instead of overwriting it.

A campaign ordinal identifies the campaign inside each 64-bit event identifier.
Ordinals must be unique among campaigns whose events can enter one merge.
New campaigns use distinct ordinals by convention, although separate campaigns never merge.
`generation/producer/HeavyFlavourUtils.h` defines the event-identifier layout.

Campaign submission requires an explicit ordinal.
`Makefile` declares no ordinal default and stops every submit target when it is absent.
This rule prevents the submitter from packing an implicit value irreversibly into event identifiers.

Seed derivation version 2 uses

```text
100000001 + 10000000 * campaign_ordinal
          + 1000000 * tune_index
          + 100000 * attempt
          + job_index
```

`tools/campaign.py` defines this formula, ten possible attempts, and PYTHIA's accepted seed range.
It makes every campaign, tune, attempt, and job tuple deterministic and distinct within the supported domain.

The renderer reserves seeds in the append-only ledger when it renders a submit file.
It refuses a duplicate within the render or a seed already present in the ledger.
A rendered submit file consumes its seed even when it never reaches the batch system.

Rendered production jobs begin deliberately held.
The submitter can inspect the complete queue before one explicit release starts generation.
`tools/render_production_submit.py` also installs exit and runtime holds, separating initial parking from later job failure.

An attempt is one try at a job and uses a fresh deterministic seed.
The worker records its inputs, producer exit, partial-file digest, validation evidence, and promotion result under `attempt_metadata/` and `raw_validation/`.
A failed attempt never overwrites or promotes a stable raw file.

Retry logic may derive an ordinal only from one campaign's existing attempt metadata.
`tools/resubmit_held.py` refuses mixed ordinals and requires an explicit ordinal when no metadata exists.
It also derives a systematic card variant from existing attempts, preventing a nominal retry from entering a variation campaign.

## Raw validation and canonical manifests

Raw promotion requires successful production and raw validation.
The worker makes the partial read-only, runs `Validation/validate_raw_output.sh`, and writes a receipt and validation log.
It then renames the partial without overwriting and writes the promoted raw-file digest.

Canonicalization fixes the ordered raw-file union after promotion.
`tools/build_canonical_manifest.py` enumerates stable raw files, requires equal tune exposure, and requires divisibility across ten blocks.
It orders rows tune-major with contiguous canonical slots and assigns `block = canonical_slot % 10`.

The builder writes `canonical_manifest.jsonl`, ten `block_NN.jsonl` files, and `freeze_seal.json`.
Each manifest row binds the raw path and digest to its attempt metadata, receipt, contracts, tune, seed, and slot.
Each block manifest contains complete rows from the central manifest, never fragments of events.

Publication processing uses manifest membership only.
`generation/submit/submit_status_analysis.sh` rejects directory discovery, first-completed selection, and unlisted reserve files.
`tools/render_analysis_submit.py` rechecks every raw digest and receipt before it renders Stage 2.

The selected central and variation manifests do not travel in this repository.
Their selector rows name external manifest, raw, analysis, and merged-product locations.
Consequently, this checkout can inspect the contracts but cannot independently recount those external file unions.

## Reduction to pair directories

Stage 2 performs one reduction over each manifest-selected raw file.
`analysis/status_analysis_THnSparse_qq.C` opens that raw file read-only, scans it once, and writes all 300 registered pair files.
Each file represents one trigger-species and associate-species combination from the expanded pair registry.

Normal canonical reduction processes every event in its raw file.
`analysis/run_status_analysis.sh` defaults to event-filter modulo zero and remainder minus one.
The event-modulo mode remains a separate diagnostic and does not create the published blocks.

The analysis submit renderer maps each canonical slot to one pair directory.
It pins the raw digest, manifest digest, reduction commit, macro digest, campaign, tune, and logical job identity.
The reduction refuses any mismatch before filling objects.

The wrapper writes into an attempt-unique staging directory.
It requires one clean summary, validates the complete directory, writes job metadata, and rechecks its checkout.
It promotes the directory only when the final path remains absent.

Every pair directory must contain the exact 300 registered filenames.
`Validation/ValidatePairDirectory.C` checks the object contract in both directions, metadata consistency, object types, pair identities, and accounting.
The wrapper also requires 12 trigger-copy groups with 288 identity comparisons and one multiplicity group with 299 comparisons.

The pair files declare `paul_pair_objects_primary_ground_v3` and carry the 202-species objects.
As of the 2026-08-21 remediation, the wrapper derives the job-sidecar schema from the producer's `kAnalysisSchema` declaration and refuses a declaration absent from the pair-object contract.
`Validation/ValidatePairDirectory.C` reports the one common schema found across all 300 files, and `tools/validate_analysis_outputs.py` requires that value to equal `analysis_job_metadata.json`.
Existing external job sidecars predate this repair and have not been revalidated or regenerated here.

## Merging centrals and blocks

Stage 3 turns 3,000 pair directories into 33 merged products.
Each tune receives one central over 1,000 input files and ten blocks over 100 files each.
Three tunes therefore produce three centrals and 30 blocks.

`merging/merge_root_files.sh` derives this shape from the sealed manifests.
It requires equal event exposure, uses the central and block slots exactly, and never discovers extra pair directories.
`merging/MergeCanonicalAnalysis.C` performs object-aware addition under the generated pair-object contract.

The caller must set `HADRONIZATION_EXPECTED_PAIR_SCHEMA`.
The merge driver supplies no default and resolves the requested tag before expensive work begins.
Use `v3` for Run 3 and all seven systematic variations; use `v2` only for an explicit legacy reduction.

Each merge leg writes to a staging directory.
The driver validates its pair inventory, objects, source manifest, input count, and provenance before promotion.
On a rerun, it accepts an existing merged product only after the same validations pass.
It refuses to overwrite an invalid existing destination.

Closure runs after all merge legs pass.
The v3 closure checks 2,100 content-and-`Sumw2` comparisons and 1,500 invariant comparisons across 300 pair files.
The closure wrapper derives these counts from the requested schema and generated object contract.
It rejects a complete v2 product when the campaign requires v3.

The object contract separates presence, scope, merge semantics, closure, and invariant identity.
For example, `hFlavourClosureSummary` is conditional because a trigger can have zero weight in a job.
Required additive objects enter closure, while required invariant objects must match across the central and ten blocks.

## Extraction and result products

Stage 4 projects merged products onto the fixed 202-species axis.
`extraction/extract_species_decomposition.py` first requires the exact 300 pair filenames from the expanded registry.
It then checks every pair file's ordinal digest against `646f310f78126267` and refuses unknown ordinals.

Flavour-closure objects belong to triggers and appear in every pair file sharing that trigger.
The extractor requires those copies to agree, then sums each trigger once.
The current registry creates 24 copies for each charm trigger and 26 for each beauty trigger.

One extraction writes `per_species.csv`, `per_category.csv`, and `per_observable.csv`.
It checks structural category closure and mapped-weight conservation before writing results.
The required v2 decay map performs the branching-fraction-weighted ground-state regrouping.

Central and ten-block tables feed block statistics.
`extraction/decompose_with_block_sems.py` calculates structural and experiment-comparable summaries from those eleven directories.
`extraction/three_tune_table.py` places the three tunes on a common row set.

Committed extraction products live under `evidence/` and `results/systematics/`.
These products let result and figure scripts run without external ROOT files.
They do not recreate the raw-to-merge part of the chain.

The tracked Stage 4 orchestration is portable at the code boundary.
`extraction/pipeline/tune_chain.sh` requires external merged and output roots,
resolves its tracked extraction entrypoint from the checkout, and refuses a
missing callee. Closure or extraction failure stops the chain. The external
ROOT products remain the unavailable part of a full execution.

## Systematic variation processing

Stage 1 defines seven generation-dependent variations in `config/systematics_variations_v1.json`.
Each variation changes exactly one setting from every nominal tune card.
`tools/make_systematic_cards.py` generates 21 cards and refuses a zero-change or multi-change card.

| variation | campaign | changed setting |
|---|---|---|
| `mur_up` | `HF_SYS_MUR_UP` | `SigmaProcess:renormMultFac = 2.0` |
| `mur_down` | `HF_SYS_MUR_DOWN` | `SigmaProcess:renormMultFac = 0.5` |
| `muf_up` | `HF_SYS_MUF_UP` | `SigmaProcess:factorMultFac = 2.0` |
| `muf_down` | `HF_SYS_MUF_DOWN` | `SigmaProcess:factorMultFac = 0.5` |
| `pdf_cteq6l1` | `HF_SYS_PDF_CTEQ6L1` | `PDF:pSet = 8` |
| `pthat_1p0` | `HF_SYS_PTHAT_1` | `PhaseSpace:pTHatMin = 1.0` |
| `pthat_4p0` | `HF_SYS_PTHAT_4` | `PhaseSpace:pTHatMin = 4.0` |

The retained run record reports 300 raw files per variation campaign: 100 per tune at 100,000 events each.
Thus, each variation contains 10 million events per tune and 30 million events across the three tunes.
`docs/SYSTEMATICS_HARVEST_RUN_RECORD.md` records the completed shape and merge receipts.

The external variation manifests and raw files are unavailable in this checkout.
The repository can derive the registered shape and verify downstream committed results, but it cannot recount all 2,100 raw files.
The retained run record supplies this file-count claim; the claim remains independently unverified.

The retained run record reports the same reduction, 33-leg merge, closure, and plotting instrument for each variation.
`tools/make_harvest_configs.py` copies the common observable and display contract from the central plotting configuration, while binding storage routes and complete-root tags to each campaign's active dataset selector.
The variation selectors require v3 and keep `publication_eligible` false.

As of the 2026-08-21 remediation, all seven committed variation configurations pass the generator check.
The authoritative storage root is each active selector's `analyzed_data_base`; all eight current physics and variation selectors agree on that route.
The authoritative label at the exact 59.85 transcribed boundary is `59.8`, recomputed from the committed MONASH minimum-bias sample by the shared class-label formatter; `59.9` is rejected by the display-filter regression.
These source/configuration repairs do not revalidate the external selected files and do not make historical renders current reproductions.

The plotting harvest emits signed variation measurements.
Extraction scripts compare each variation with nominal, select source contributions, and combine compatible sources.
The resulting CSV and JSON products live under `results/systematics/20260819/` and `results/systematics/20260820/`.

## Plotting and figure production

Stage 5 has one scientific figure path: ROOT plotting over a named validated dataset.
The ROOT entry point is `plotting/run_paper_plots.sh`.
Its configurations select merged products, pair objects, multiplicity classes, canvases, and output locations.
Accepted publication bytes have one canonical destination, `results/figures/main/`.
The current external central and ten-block inputs, accepted bytes, and final receipts do not travel with this checkout.

The runner currently creates candidates without final-plot provenance
sidecars. `results/provenance/figure_acceptance_manifest_v1.json` records eight
candidate roles and accepts none. A separate receipt harvest and visual review
must close each role after the ROOT workflow completes.

Current v3 pair files already contain the trigger and associate kinematic selections.
The ROOT plotter validates that metadata and applies the requested multiplicity projection without repeating those cuts.
Mixed metadata or an undeclared recut stops the canonical plotting path.

The ROOT path also carries the ten-block uncertainty instrument.
It forms opposite-sign minus same-sign quantities inside each block and reports the standard error across ten block estimators.
The central value still comes from the pooled central merged product.
Trigger normalization comes from the dedicated `hTrKinematics` object, not from a trigger-momentum projection of a pair correlation.

The combined selector declares no default dataset and refuses to choose one.
A caller can set `HADRONIZATION_DATASET=<key>` or point `DATASET_SELECTOR` at a per-campaign selector with its own `active_dataset`.
This explicit choice prevents a variation render from silently reading the central campaign, which happened for five renders.

The selector exports `HADRONIZATION_CAMPAIGN` with the selected dataset.
The canonical raw plotting consumer compares that value with every manifest row's campaign identity.
Without this binding, another campaign's valid sealed freeze could satisfy every internal manifest check.

Measurement targets and publication targets have separate contracts.
The `measure-balancing` target accepts a `systematic_variation` and requires a dedicated measurement output root.
A systematic variation supplies an uncertainty input; it is not a publication dataset.

Publication targets accept only `canonical` and `canonical_candidate` dataset statuses.
An authorized `canonical` row must be publication-eligible, while a `canonical_candidate` row must remain ineligible.
The runner rejects a command that mixes measurement and publication targets.

The main THnSparse macro stages PDF, PNG, and generated-C outputs beside their final directories.
It writes a passing multiplicity-boundary receipt only after the requested plotting workflow succeeds.
Only then does `plotting/improvedPlotting_THnSparse.C` promote the staged outputs.

`plotting/TunePlotStyle.h` fixes the tune presentation.
MONASH uses black marker 20, JUNCTIONS uses blue marker 21, and CLOSEPACKING uses purple marker 22.
All three tune curves are solid; line style distinguishes multiplicity classes where required.
Configurations cannot replace these styles for a known tune.

Accepted scientific figures come only from the ROOT plotting path above. Compact committed
tables support numerical review, but they are not a substitute for the
scientific canvases, their ten-block uncertainties, and their dataset-bound
receipts.

## Promotion, failure, and schema evolution

Every mutable stage writes outside its final destination first.
Generation, reduction, merging, and THnSparse plotting promote only after their boundary validations pass.
Destinations are write-once: a valid output resumes work, while an invalid output stops it.

Validators reject missing, additional, stale, mixed, or unknown contract values.
The pair-object contract recognizes only `paul_pair_objects_primary_ground_v2` and `paul_pair_objects_primary_ground_v3`.
Consumers parse those tags through the generated header and have no fallback for an unknown schema.

Schema negotiation is exact in both directions.
A correct v2 pair file omits the v3 species objects, while a correct v3 file requires them.
The expected-schema input prevents an internally consistent v2 campaign from passing a v3 closure requirement.
Negative tests in `tests/test_pair_object_contract.py` and `tests/test_closure_schema_requirement.py` protect this behaviour.

A new pair schema requires one coordinated contract change.
Add its tag and version to `config/pair_file_object_contract_v1.json`, assign each new object's first schema, and regenerate the header.
Then update the reduction producer, caller-supplied expected schema, configurations, fixtures, and negative tests.

Raw schema `hf_primary_ground_raw_v7` remains a separate boundary.
The current reduction rejects any other raw schema, so relabeling an earlier raw file cannot make it current.
A downstream-only question can rerun reduction from v7 raw files when those files contain every required field.

A raw-schema change requires new raw files when fields or meanings change.
It also requires a new producer contract, raw validator, manifest contract, reduction reader, and compatibility decision.
No consumer may infer compatibility from a filename or shared branch name.

A new tune requires more than another tune card.
Update the published tune tuple, tune ordinals, campaign rendering, manifest validators, merge loops, selectors, configurations, extraction tables, styles, and tests together.
Current production and several downstream loops explicitly enumerate MONASH, JUNCTIONS, and CLOSEPACKING.

The repository favors refusal over silent schema evolution.
This rule keeps a plausible output from crossing a boundary under the wrong campaign, schema, registry, or dataset identity.
