## 4. A latent macro bug that only three tunes could expose

**Found by looking at the first rendering**, not by any check in the stack.

`drawBalancingPlots` set the x-axis bin labels under `if (i==0)`, where `i`
indexes the **global** tune list, while the loop `continue`s past tunes not on
the current canvas:

```cpp
for (Int_t i=0; i<nTUNES; i++) {
    std::string TUNE = vTUNES[i];
    if (!isInVector(TUNE, vCanvasTUNES)) { continue; }
    ...
        if (i==0) { hYieldsTemplate->GetXaxis()->SetBinLabel(1+j, associateName.c_str()); }
```

A canvas whose only tune is JUNCTIONS skips `i=0` (MONASH) at the `continue` and
**never reaches the branch**, so it rendered with a bare numeric 0–2 axis
instead of associate names. The first rendering showed labels on the MONASH row
and on the two ratio rows — which carry MONASH as their denominator, hence
`i==0` — and none on the JUNCTIONS and CLOSEPACKING rows.

**It could not show before.** Every earlier configuration either had one tune
globally or put MONASH first on every canvas. `drawBalancingPlotsTUNERatios`
sets the labels unconditionally and was never affected.

The guard is now a per-canvas flag set after the first *drawn* tune, which is
what the original comment ("only set the template histogram once") intended.
All ten panels carry their labels in the run recorded here.

## P4. Two design decisions — RULED 2026-08-17, both REJECTED

Both were rendered rather than chosen silently, put to the owner, and **both are
rejected. The canvas as described above is the shipped layout**, unchanged by
the rulings. The two renders are kept beside this file as
`REJECTED_variant{A,B}_*.png` — considered-and-rejected evidence, not options
still open.

### Variant A — log ratio panels: **REJECTED**

`REJECTED_variantA_log_ratio_panels.png`. **Ratio panels stay linear.**

> **Owner ruling: near-unity ratios label badly on log.** The rendered variant
> shows it — the axis reads `6×10⁻¹, 7×10⁻¹, 8×10⁻¹, 9×10⁻¹, 1, 2`, scientific
> notation for numbers around one, against a linear `0.6, 0.8, 1.0 … 2.4`.

This matches the recommendation this run record offered, and the measured spread
is why: **0.6605–2.2837**, a factor 3.5 end to end. Log earns its place when a
ratio axis spans decades; this one does not.

### Variant B — MONASH-first ordering: **REJECTED**

`REJECTED_variantB_monash_first_ordering.png`. **The two ratio panels stay
grouped**, adjacent at the bottom of the stack.

> **Owner ruling: the paper's central comparison is ratio-vs-ratio.** Variant B
> moves each CR tune's ratio row up under the tune it divides, which separates
> `JUNCTIONS / MONASH` from `CLOSEPACKING / MONASH` by two intervening yield
> rows. Those two panels are the comparison the paper is making, so they must be
> readable against each other without the eye crossing anything.

**This is a better reason than the one this record offered**, which treated the
ordering as a readability preference and declined to recommend. It is not a
preference: it follows from what the figure is for. Recorded here so the next
person to propose baseline-first ordering finds the argument rather than
re-running the variant.
